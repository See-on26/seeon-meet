# 지연·실시간 삽입 모드의 온라인 전환

> 2026-08-11 작성. **사람이 읽는 설명서**다. 무엇을 왜 이렇게 짓는지, 그리고
> 영상 업로드 방식에서 무엇을 가져오고 무엇을 버리는지를 답한다.
>
> 예전 번호로는 1.2 지연 / 1.3 실시간[1]이다. 제품 화면에서는 번호를 뺐다.

## 1. 무엇이 막혀 있었나

실험실 앱은 **업로드한 영상 파일**을 틀면서 캡션 체인을 태운다.
여기서 "지연"을 만드는 방법은 놀랍도록 단순했다.

> 같은 파일을 재생하는 `<video>` 요소를 **하나 더** 만들고,
> 그 요소의 `currentTime`을 10초 뒤로 둔다.

앞의 요소(라이브)는 화면에 안 보이고 ASR·VLM이 분석만 한다.
뒤의 요소(지연)가 사용자가 보고 듣는 것이다.
캡션을 넣을 때가 되면 뒤 요소를 `pause()`하고, 나레이션이 끝나면
`playbackRate = 1.4`로 늘어난 지연을 회수한다.

**이 방식은 "되감을 수 있는 URL"이 있어야만 성립한다.**
실회의에서 탭 캡처로 얻는 것은 `MediaStream`이고, 그것은 흐르는 물 같아서 되감을 수 없다.
`pause()`를 걸면 버퍼링이 아니라 그냥 소리가 **사라진다.**
`playbackRate`는 아예 무시된다.

호출부 한 줄이 이 사실을 그대로 드러낸다.

```js
delayBuffer.start({ sourceUrl: captureSource.objectUrl, fromTimeMs });
//                              ^^^^^^^^^^^^^^^^^^^^^^ 실회의엔 이게 없다
```

그래서 제품 레포에서는 이 세 모드가 **코드로 봉인**돼 있었다 —
`startDelayBufferIfNeeded()`가 첫 줄에서 그냥 `return`했고, 모드 버튼이 전부 회색이었다.

## 2. 해법을 한 문장으로

> **되감을 수 없는 스트림을, 되감을 수 있는 미디어 요소로 바꿔서 준다.**

`MediaRecorder`로 회의 오디오를 계속 녹화해 `MediaSource`에 밀어 넣으면,
`<audio>` 요소가 그 위를 10초 뒤에서 재생한다.
**요소가 생기는 순간 `pause()`도 `playbackRate`도 다시 살아난다.**

```
탭 캡처 MediaStream ─┬─▶ [분석] ASR·VLM·ROI                      ← 최전선, 지연 0
                     │
                     └─▶ MediaRecorder(오디오만, 0.2초씩)
                            └─▶ MediaSource ─▶ <audio> ─▶ 스피커  ← 사용자, 10초 뒤
```

여기서 결정적인 부수 효과가 하나 있다.
**`<audio>` 요소의 배속은 음높이를 보존한다**(`preservesPitch`가 기본 켜짐).
링버퍼를 직접 만들어 빨리 읽는 방식이었다면 1.8배에서 만화 목소리가 났을 것이다.
미디어 요소를 얻는 것 자체가 목적이었던 이유다.

## 3. 영상 업로드에서 **그대로 차용한 것**

놀랍게도 대부분이 살아남는다. **바뀌는 것은 재생 매체 하나뿐**이다.

### ① 핵심 착상 — "지연 버퍼가 곧 룩어헤드다"

사용자는 최전선보다 10초 뒤를 듣는다. ASR·VLM은 최전선을 처리한다.
따라서 **파이프라인이 10초 안에 끝나면, 사용자가 그 지점에 도착하기 전에 캡션이 준비된다.**
삽입은 미래 예측이 아니라 재생 시계에 대한 스케줄링이 된다.
이 논리는 매체와 무관하게 성립한다.

### ② 계산 로직 — 한 줄도 안 바뀐다

| 함수 | 하는 일 |
|---|---|
| `computeActualDelayMs` | 라이브 − 재생 = 실제 지연 |
| `computeCatchupRate` | 초과 지연이 클수록 배속을 올리되 모드 상한으로 클램프 |
| `computeCatchupDurationMs` | 회수에 걸릴 시간 = 초과 ÷ (배속−1) |
| `computeInsertWaitMs` | 사용자가 그 지점에 도달할 때까지 남은 시간 |
| `isCaptionStale` | 이미 지나쳐 버린 캡션인가 |

이유는 이렇다. 파일 모드의 "최전선 시계"는 라이브 요소의 재생 위치였고,
스트림 모드에서는 **녹화기가 지금까지 밀어 넣은 총 길이**다.
이름은 다르지만 **둘 다 "아직 안 들려준 지점"**을 가리킨다. 그러니 뺄셈이 그대로 맞는다.

### ③ 제어 규칙 — "어느 방향으로도 시크하지 않는다"

이게 이 모듈에서 가장 값진 부분이다.

- **앞으로 감으면** 사용자가 아직 안 들은 구간을 건너뛴다
- **뒤로 감으면** 이미 들은 구간이 반복돼 청자의 시간이 거꾸로 흐른다

남는 수단은 **"멈춰서 기다리기"**와 **"배속으로 따라잡기"** 둘뿐이다.
매체가 바뀌어도 이 원칙은 그대로 지킨다.

### ④ 그 외 그대로 가는 것들

- **삽입 시점 결정** — `NarrationScheduler`, `gap-inference-agent`(틈 선택),
  `utterance-boundary-detector`(발화 경계)
- **모드 정책값 전부** — 지연 10초/0초, 배속 1.1~1.4 / 1.5~1.8, 어절 예산, 컨텍스트 창
- **버퍼 채우기 UX** — 지연 모드 시작 직후 "10초 후 시작됩니다" 준비 화면.
  이게 정상 동작이다
- **삽입 절차** — 멈추고 → 나레이션 내고 → 재개. `CaptionNarrator`가 하던 그대로
- **두 요소 구도** — 최전선은 분석 전용, 지연분이 사용자용

## 4. **버린 것**

### ① 화면 지연 — 가장 큰 포기

실험실에서는 화면도 같이 10초 밀렸다.
오버레이 캔버스가 지연 요소의 프레임을 그렸기 때문에 공짜였다.

실회의는 구조가 다르다.

```
BaseWindow
├─ meetView   ← 진짜 Google Meet 페이지. 살아 있고 클릭·채팅·마이크가 동작한다
└─ viewerView ← 컨트롤 패널. 그릴 캔버스가 없다
```

사용자가 보는 것은 캔버스가 아니라 **살아 있는 Meet 페이지 그 자체**다.
10초 지연시키려면 그 위를 덮어야 하고, 그러면 **회의 조작이 전부 막힌다.**
비용은 인코딩 부하가 아니라 이쪽이었다.

→ **소리만 지연하고 화면은 라이브로 둔다.**
시각장애인 사용자에게는 화면 정합성이 무의미하므로 감내한다.

다만 어긋나는 건 화면 하나뿐이다. 캡션은 발화 시점의 프레임을 근거로 만들어지고
삽입 지점도 그 시점의 재생 위치라, **나레이션과 소리는 서로 맞는다.**
문제가 되는 순간은 **사용자가 발언하거나 다른 참가자와 반응을 주고받을 때**다.

### ② "지연이 0이면 버퍼가 필요 없다"는 전제

파일에서는 맞았다. 라이브 `<video>`를 `pause()`하면 그게 곧 버퍼링이니까.
스트림에서는 틀리다 — 멈추면 소리가 사라진다.

→ **실시간 삽입 모드도 버퍼가 필요하다.** 다만 목표 지연이 0일 뿐이다.

이건 오히려 좋은 소식이다. 두 모드가 **같은 코드에 상수만 다르게** 돌게 된다.

| | 목표 지연 | 배속 | 최소 여유 |
|---|---|---|---|
| 지연 | 10초 | 1.1~1.4 | — |
| 실시간 삽입 | **0초** | 1.5~1.8 | 300ms |

300ms는 재생 헤드가 버퍼 끝에 딱 붙어 계속 끊기는 걸 막는 물리적 여유다.

### ③ 시작 지점 시크(`fromTimeMs`)

파일에서는 회의 중 전환 시 "사용자가 이미 들은 지점"을 넘겨 거기서부터 재생했다.
스트림은 **전환하는 순간부터 녹화가 시작**되므로 되감을 과거가 없다.
인자는 남겨 두되 스트림 소스는 무시한다.

관련해서 하나 더 — 녹화기를 캡처 시작부터 항상 돌릴 수도 있었지만 **일부러 안 한다.**
그러면 전환할 때 10초를 되감을 수 있게 되는데,
그건 이미 들은 구간을 다시 들려주는 것이라 사양이 금지한다.

### ④ 단일 시계 가정

파일에서는 모든 시각이 `currentTime` 하나로 통했다.
실회의에는 **0점이 다른 시계 두 개**가 생긴다.

| | 시계 | 0점 |
|---|---|---|
| 캡션이 달고 오는 시각 | `performance.now()` 기반 | 캡처 시작 (벽시계) |
| 재생 위치 | `<audio>.currentTime` | 녹화 시작 (미디어 타임라인) |

→ 어댑터가 오프셋을 더해 **재생 시계를 벽시계 축으로 돌려준다.**
그러면 삽입 스케줄링 호출부가 변환을 몰라도 된다.
지연 계산에서는 두 값에 같은 오프셋이 들어가 상쇄되므로 뺄셈도 안 깨진다.

### ⑤ 나레이터의 독자적 배속 회수

이건 실험실에 있던 **결함**을 정리하는 것이다.
`DelayBuffer.tick()`이 250ms마다 배속을 쓰고, `CaptionNarrator`도 배속을 쓴다 —
둘이 서로를 덮어쓴다. 파일에서는 삽입 중 요소가 멈춰 있어 증상이 가려졌다.

→ **버퍼가 있으면 나레이터는 배속을 양보한다.**
버퍼는 실측 지연으로 회수하고 나레이터는 추정치로 회수하기 때문에 버퍼 쪽이 항상 옳다.

## 5. 새로 짓는 것은 이것뿐이다

```
DelayBuffer  ── 제어 (목표 지연 유지 · 배속 회수 · 버퍼 채우기)   ← 거의 그대로
    └─ source (주입)
        ├─ FileDelaySource   : 같은 파일의 <video>            ← 기존 코드를 그대로 옮긴 것
        └─ StreamDelaySource : MediaRecorder→MSE의 <audio>    ← 유일한 신규 구현
```

`StreamDelaySource`가 하는 일은 넷이다.

1. 오디오 트랙만 녹화 (`MediaRecorder`, 0.2초 단위)
2. 청크를 **하나씩 순서대로** `MediaSource`에 넣기 (동시에 넣으면 던진다)
3. 오래된 구간 걷어내기 (목표 지연의 3배만 보관)
4. 벽시계 ↔ 미디어시계 변환

여기에 안전장치 둘을 단다.

- **캡션 드롭** — 지연이 6초 넘게 밀리면 새 캡션을 버린다.
  회수가 못 따라잡을 때 모드를 강등하는 대신 캡션을 포기한다
  (강등은 되돌릴 수 없어 대가가 크다)
- **드리프트 계측** — 두 시계가 500ms 넘게 어긋나면 로그에 남긴다.
  **보정은 안 한다** — 보정하면 삽입 지점이 튄다

모든 실패의 종착지는 **실시간 믹싱 모드로의 복귀**다.
그 모드는 버퍼 없이 라이브 스트림만 쓰므로 이 설계의 어떤 부분이 깨져도 살아 있다.

## 6. 순서

| | 단계 | 왜 이 순서인가 |
|---|---|---|
| **0** | **MSE 왕복 프로브** | 여기서 막히면 나머지가 전부 무의미하다. 다른 코드를 쓰기 전에 확인한다 |
| 1 | 테스트 환경 + 현재 동작 고정 | 제품 레포엔 테스트가 하나도 없다. 리팩터 전에 안전망을 깐다 |
| 2 | `StreamDelaySource` | 유일한 신규 구현 |
| 3 | 소스 어댑터 분리 | 동작 불변 리팩터. 1단계 테스트가 계속 통과해야 한다 |
| 4 | **지연 모드 켜기** | 봉인 해제 + 배선 |
| 5 | 회수 권한 정리 | |
| 6 | **실시간 삽입 켜기** + 드롭 게이트 | 지연 모드가 실제로 되는 걸 본 뒤에 간다 |
| 7 | 실험 레포 되맞춤 | `renderer/core/`는 공유 계층이라 갈라지면 안 된다 |

**0단계를 맨 앞에 두는 이유**를 강조하고 싶다.
선행 문서가 확인한 건 `MediaRecorder`와 `MediaSource`가 각각 opus를 지원한다는 것뿐이지,
**둘을 이어 붙인 왕복이 실제로 재생되는지가 아니다.**
MediaRecorder의 WebM 출력은 길이가 미확정(`0xFFFFFFFF`)이라
MSE가 거부하는 사례가 알려져 있다.
그래서 `tools/probe-mse-roundtrip.js` 하나부터 돌린다.

## 6.5 실회의 실측 (2026-08-12)

실제 Google Meet 회의(발표자 화면 공유)에 붙여 **지연 모드**를 실측했다.
세션 로그 `out/pipeline-1786460337157.jsonl`의 마지막 세션(1134초) 기준.

| 지표 | 값 | 판정 |
|---|---|---|
| ASR 파이프라인 지연(captureToText) | 중앙값 **263ms**, 최대 2509ms | 10초 버퍼에 여유롭게 들어감 |
| 캡션 드롭 | **0건** | 회수가 지연을 못 따라간 적 없음 |
| 재생 시계 드리프트 경고(>500ms) | **0건** | 벽↔미디어 시계 어긋남 없음(§7 리스크 안 터짐) |
| TTS 합성 | 13건 전부 성공 | — |
| 나레이션 emit | 22건 중 13건 | 미emit 9건은 전부 deixis 중복 억제(정상) |

**설계 핵심 가설 실증.** 파이프라인 지연 중앙값이 0.26초라, 10초 버퍼 안에서 사용자가
그 지점에 도달하기 전에 캡션이 준비된다. 콘솔 로그 `캡션 삽입 대기 ~10062ms`가 그대로 보여줬다.
삽입 시 지연이 최대 ~12.7초까지 벌어졌다가 배속(1.1~1.4)으로 10초로 복귀했고,
드롭·드리프트가 한 번도 발동하지 않았다 — 지연이 목표 10초 근처에서 안정적으로 유지됐다.

**주의로 남길 것.** 오래 실행된 초기 세션에서 재생 헤드가 한 지점(90초)에 멈춰 지연이
360초까지 누적된 스냅샷을 한 번 관찰했다. 깨끗한 재현(캡처 시작→지연)에서는 나타나지 않았고,
**일시정지(`delayBuffer.hold()`) 후 재개 누락** 또는 SSH 터널 끊김 구간의 부작용으로 추정한다.
`pauseExperiment`/`resumeExperiment`의 재생 헤드 복귀는 별도 확인 대상이다.

**실시간 삽입 모드는 아직 실측하지 않았다.**

## 7. 이 작업이 답하지 않는 것

- **청취 모드(60초)** — 이 구조에서 상수 하나로 거의 공짜가 되지만
  (60초 opus ≈ 180KB) 이번 범위가 아니라 켜지 않는다
- **화면 지연** — 포기했다. 되살리려면 `meetView`를 덮지 않는 별도 미리보기가 선행되어야 한다.
  어느 프레임을 그려야 하는지는 이미 알고 있으므로, 비디오 트랙까지 녹화하도록
  `StreamDelaySource`를 늘리고 그 `<video>`를 컨트롤 패널에 붙이면 된다
- **배속 청취 비율** — 실시간 삽입에서 회의 시간의 19~30%를 빨리 감아 듣게 된다.
  감내 가능한지는 실측 후에 판단한다. 넘치면 캡션 밀도를 낮춰야 한다
